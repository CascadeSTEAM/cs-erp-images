## Summary

Started as "help me understand CS-0061" and ended with the ticket resolved. The ticket was
real and worse than it read. All background jobs on `new.cascadesteam.org` had been failing
with MariaDB error **1045** since the site was created on 2026-07-22 — **39 of 39 Scheduled
Job Types had `last_execution = NULL` and `Scheduled Job Log` was empty. Not one scheduled
task had ever run on that site.** The scheduler had been erroring every four minutes for nine
days straight across 21 rotated log files.

Root cause: the site's MariaDB account `_4306fc09495277f5` had a grant for **exactly one
host — `172.18.0.8`, the backend container's IP.** Frappe's MariaDB `setup_db` derives the
grant host from `SELECT USER()` at `bench new-site` time, so the account got pinned to
whichever container happened to run site creation. The workers and scheduler run in different
containers (`queue-short 172.18.0.9`, `queue-long 172.18.0.5`, `scheduler 172.18.0.7`) and had
no grant at all. `support.cascadesteam.org` was unaffected because its account already carried
a `'%'` row.

Fixed at **2026-08-01 04:00:46 UTC** by adding the matching `'%'` grant, copying the existing
password hash server-side so no plaintext was ever handled. No container restart, no config
change, no touch to the existing IP-pinned row.

## Evidence that settled it

The decisive test was `SELECT current_user()` for the same site, using the same
`site_config.json` on the same bind mount, from each container in turn:

| Container | IP | Before | After |
|---|---|---|---|
| backend | 172.18.0.8 | OK | OK (still matches the narrower row) |
| queue-short | 172.18.0.9 | 1045 | OK as `@%` |
| queue-long | 172.18.0.5 | 1045 | OK as `@%` |
| scheduler | 172.18.0.7 | 1045 | OK as `@%` |

One password, two outcomes, split exactly on the grant boundary — which ruled out the password
theory immediately. Stale volumes, divergent worker env, Redis reachability, DNS, missing
database and a paused scheduler were each ruled out with direct evidence.

Verification after the fix: control job `frappe.enqueue("frappe.utils.change_log.get_versions")`
reached terminal status **`finished`**; four consecutive clean scheduler ticks; `last_execution`
now **39/39 non-NULL**; 44 `Job OK` lines across both queues with zero exceptions and zero new
1045s.

## Decisions

- **`'%'` over `'172.18.%'`** — matches how `support.cascadesteam.org` is already provisioned
  and what upstream `frappe_docker` ships. The tighter pattern would re-break if Docker
  recreated the bridge on a different subnet. MariaDB publishes no host port, so `'%'` is
  reachable only from the internal bridge network.
- **Left the redundant `@172.18.0.8` row in place** — it is the last remaining evidence of how
  this happened. Removing it should be a separate, deliberate decision.
- **Discarded the 17 stale failed jobs rather than requeuing** — replaying week-old
  `execute_action` / `delete_dynamic_links` payloads against a since-changed site is riskier
  than losing them. The 14 unrelated `support` failures were verified intact.
- **Diagnosis was strictly read-only; the fix was applied only after explicit owner approval.**
  All live access went through OpsKit subagents per policy.

## Two traps this session hit, worth not re-learning

- **`db.set_value` bypasses the controller.** Setting `status = "Resolved"` that way left
  `status_category = "Open"` and `resolution_date` NULL. `status_category` is what the Helpdesk
  agent-home and all four default views actually filter on, so the ticket would have read
  Resolved while still sitting in every Open queue. Also `set_status_category()` only fills
  when the field is empty, so a plain `doc.save()` will not re-derive it — the field has to be
  nulled first. Transition ticket status through the document API.
- **`System Settings.time_zone` is still blank on `new.cascadesteam.org`**, so Frappe-sourced
  timestamps read IST (+5:30) while container and OS timestamps are UTC. Measured at exactly
  +5:30 from a single process. A naive comparison during verification would have manufactured a
  false positive — a job that ran *before* the fix looking like it ran after.
